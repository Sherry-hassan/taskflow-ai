## Changelog

* **2026-10-10 (M0 audit)** — Re-audited the M0 scaffold against `implementation-plan.md` v0.2 §2 and actually re-ran every verification command from a clean state. Found and fixed three real issues (none were pre-existing scope additions — all within the approved M0 scope):
  1. **Node/engine incompatibility**: `vitest@5.0.3`'s own `engines` field requires `^22.12.0 || ^24.0.0 || >=26.0.0` — it explicitly excludes Node 20.x and 23.x. `.github/workflows/ci.yml` was pinned to `node-version: 20`, which satisfies `vite`/`@vitejs/plugin-react`'s wider range but **not** vitest's. Fixed by changing CI to Node 24 (matching local dev, which runs 24.15.0) and adding an `engines` field to the root `package.json` so this class of mismatch is caught by `npm install`/`npm ci` automatically going forward. Verified via static inspection of each installed package's own `package.json` `engines` field (`node -e "require('./node_modules/<pkg>/package.json').engines"`) — not by executing under Node 20 itself, since only Node 24.15.0 is installed in this environment; no other Node version was available to reproduce the CI failure directly.
  2. **ESLint was linting the build output**: after `npm run build` had run once and produced `client/dist/`, a subsequent `npm run lint` failed with 96 real errors — all inside the minified `dist/assets/index-*.js` bundle, because `client/eslint.config.js` had no `ignores` entry for `dist/`. Fixed by adding `{ ignores: ['dist/**'] }` as the first entry in that config. Re-verified lint passes both before and after a fresh build, confirming the fix holds with `dist/` present.
  3. Updated `README.md`'s Node version prerequisite from "20+" (inaccurate) to the real range enforced by the new `engines` field.
  * **Verification commands actually executed this session** (clean `npm ci` first, then each command run again in isolation to capture its own exit code): `npm ci` → exit 0; `npm run lint` → exit 0 (both packages); `npm run build` → exit 0 (`client/dist/` produced, `server` syntax check passes); `npm test` → exit 0 (3 test files, 3 tests); `npm audit` → exit 0, **0 vulnerabilities**.
  * **MongoDB replica-set setup — actually verified, not assumed**: this machine has a pre-existing MongoDB 8.3.7 Windows service on port 27017, running **standalone** (no `replication:` block in its config) — this was left untouched throughout. Instead, a disposable, project-scoped replica-set instance was started in a scratch directory on port 27018 (`mongod --replSet rs0verify --dbpath <scratch> --port 27018`), initiated via the equivalent of `rs.initiate()` (the `replSetInitiate` admin command, since no `mongosh` binary is installed here — only `mongod.exe`), confirmed to reach `PRIMARY`, and then used to **actually commit a real multi-document transaction** across two collections via the MongoDB Node driver (`session.withTransaction(...)`) — which succeeded. As a control, the **same transaction attempted against the pre-existing standalone instance on 27017 failed** with the expected driver error ("Transaction numbers are only allowed on a replica set member or mongos"), directly substantiating `system-design.md` §1's claim. The disposable instance was then stopped and its data removed; the pre-existing system service on 27017 was confirmed still running, untouched, throughout. **Exit criterion 6 is now genuinely satisfied** — not just documented, but executed and observed.
  * **GitHub Actions — still blocked, not run**: `git log`/`git remote -v` confirm this repository has **no commits, no branches, and no remote** at all. There is nothing to push and nothing for a GitHub Actions workflow to run against. `.github/workflows/ci.yml` runs the same four commands just verified locally (`npm ci`, lint, build, test) and is believed correct, but this is **not** the same as an actual green run — that requires, in order: (1) `git add` + an initial commit, (2) creating/connecting a GitHub remote, (3) `git push`, at which point the workflow fires automatically on push per its `on: push` trigger and a real result can be reported. None of those three steps were taken — committing, creating a remote, and pushing are git/repository-level actions outside this audit's explicit scope and were not authorized.
  * M0 status: **In progress** — exit criteria 1–6 verified; criterion 7 remains the sole blocker, and it is a repository-setup blocker (no commit/remote), not a code or configuration defect.
