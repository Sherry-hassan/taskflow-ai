Fixed as a drafting-error correction (`test-strategy.md` v0.2 → v0.3); CSRF middleware was built per the corrected, consistent version.
  * **Real bugs found by actually running the tests, not assumed away**:
    1. A bug in my own first draft of `rotateRefreshToken` (an unreachable-code placeholder) — caught before ever running anything.
    2. Express 4 does not forward a rejected promise from an async route handler to the error middleware — added a standard `asyncHandler` wrapper; without it, an unexpected error would have hung the request instead of returning 500.
    3. `database-design.md`'s `RefreshToken.replacedBy` field wasn't being set — fixed to set it atomically alongside `revokedAt` during rotation, per spec, using a pre-generated ObjectId.
    4. React Testing Library wasn't auto-cleaning between tests (no implicit global `afterEach` for it to detect) — two forms accumulated in the same jsdom document across tests. Fixed with an explicit `cleanup()` in the Vitest setup file.
    5. `Secure`-flagged cookies cannot round-trip through Supertest's in-process HTTP agent (no real TLS) — every CSRF test failed with 403 on the *second* request in a flow. Fixed with the standard `secure: NODE_ENV === 'production'` pattern (not a weakening of FR-007 — a Secure cookie literally cannot function over plain HTTP regardless of who sets it; production is unaffected).
    6. `authRoutes.js`'s rate limiters were module-level singletons — every `createApp()` call (including a "fresh app per test" fix I tried first) shared the exact same limiter state forever, since the shared singleton router/limiters live in the cached module, not the app instance. Fixed by converting the router into a `createAuthRouter()` factory called fresh inside every `createApp()`.
    7. One test's own expectation was wrong, not the app: after logout, `refresh` correctly fails at the CSRF layer (403, cookie cleared) rather than the refresh-token layer (401) — fixed the test's assertion, not the app.
  * **Documented, not silently fixed**: `rotateRefreshToken` has a narrow residual timing window (commented in the code) where, under a very particular concurrent-request interleaving, a reuse sweep could complete before a winning request's brand-new token is inserted, letting that new token escape revocation. Closing it fully would need a family-level "compromised" marker — a `database-design.md` schema addition outside this milestone's approved scope — so it's flagged, not patched silently. The deterministic guarantees (exactly one of two concurrent rotations wins; sequential reuse-of-a-stale-token revokes the whole family, successor included) are implemented and tested; this specific race is not.
  * **Test-placement note**: `test-strategy.md` §3 lists "refresh-token rotation logic" as a unit-test target; per that same document's own §1 design decision ("atomic conditional updates... only manifest with a real database"), the rotation/reuse/concurrency guarantees are instead tested at the API/Integration level against a real MongoDB — §3's unit coverage for this area is limited to the pure, DB-independent pieces (access-token sign/verify shape, crypto helpers).
